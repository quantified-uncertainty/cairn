# Stacks Browser architecture

How the pieces fit, for anyone adding a feature. The README covers running and using it.

## Server (`server.mjs`, `server/`)

- `server/config.mjs` exports `HERE`, `PORT` (`--port N` or `STACKS_PORT`), `CACHE` (`STACKS_CACHE`, default `~/.cache/open-stacks`), `MODEL` (`STACKS_MODEL`), `UA` and `hasKey()`.
- `server/cache.mjs` is the disk cache for open sources: `allowed(url)`, `cached(url)`, `ensure(url)` (fetch once into the cache), `meta(url)`, `read(url)`, `paths(url)`, `key(str)` (sha1), `enqueue(urls, pri, group)` (the prefetch queue) and `stats`. `onDead(fn)` lets `server/rescue.mjs` replace a document that fails for good (404, 410, 451, a vanished host) or now serves a placeholder page with its Internet Archive copy, inside `ensure`, so every caller gets it.
- `server/routes/*.mjs` load in name order. Each exports `default function (app)`; `app` has:
  - `route(method, pathOrRegExp, async (req, res, url, match) => {})`, where method is `'GET'`, `'POST'` or `'*'`;
  - `status(() => ({...}))` to add fields to `GET /status`;
  - `onStart(fn)` to run after the server starts listening;
  - helpers `json(res, obj, code)`, `send(res, code, body, type)` and `body(req)` (parsed JSON);
  - `cache`, `CACHE`, `HERE`, `MODEL`, `UA` and `hasKey`.
- `GET /ready?ids=` (`server/routes/13-ready.mjs`): per item, `[first, frac]`: whether the spread it opens at is on disk, and the share of it on disk (books: their pages, sampled). The Library dims items not fetched yet and shows a percentage for books partly fetched.
- The warm-up (`server/routes/60-warm.mjs`) fetches the opening spread of every item, in the order you will see them: first the next 80 items of the stack you are walking (`ahead`, sent by `features/telemetry.js` when the stack changes or you move 15 items on), then every lane in its own sort. `STACKS_WARM_MB` (default 3000) caps it.
- Static files come from `ui/`. `/corpus.json` and `/enrich.json` (optional) come from the browser folder. `/features.json` lists `ui/js/features/*.js` and `ui/features/*.css`.

## Client (`ui/js/`)

`main.js` imports the core modules, then every feature module listed in `/features.json`, then calls `boot()`. A feature is one file in `ui/js/features/` plus, optionally, one stylesheet in `ui/features/`. Prefer adding a feature over editing core files.

### Hooks (`util.js`)

- `on(name, fn)` and `emit(name, detail)` drive an event bus. The events are:
  - `item:shown {i, it}`;
  - `item:skim {i, it}`: a step of hold-to-skim (`riffle.js`: holding `j`/`k` steps through the stack showing each item's title and, when at hand, first page); not a visit, nothing loads, and only the item released on gets `item:shown`;
  - `spread:rendered {i, it, s, els, doc, flow?}`; for rasters, `els[j]._pnl` is the panel and `els[j].dataset.k` the page;
  - `summary:updated {id, summary}`;
  - `nav {type, i, it, ...}`; types: `item`, `turn`, `page`, `random`, `zoom`, `back`;
  - `nav:before {label, i, pos, s, hist, zoom, order?, aff?, saved?, lane?, stk}`, where you were just before a move or judgment (`features/back.js` keeps them for Back; `stk` is the stack you were in, added by `stack.js`, and Back hands the snapshot back as `nav {type: 'back', undone, snap}` so the stack is restored too);
  - `stack:changed {stack}` (`stack.js`: after a sort change, a stay-in, leaving, `goTo` and a lane switch) and `stack:show {stack}` (the header crumb was clicked: `features/library.js` shows the stack);
  - `gesture:step {axis, dir, device, fresh}` and `gesture:pinch {dir, x, y}` (`gesture.js`); a step listener sets `stop` to end the gesture;
  - `view:changed {view}`;
  - `panel:painted`, `status`, `boot` and `flow:jump`;
  - `memory:updated {id}` (`features/memory.js`, which also exports `progressOf(id)` → `{seen, n, frac, far, at, done, ms, visits, …}` or null);
  - `overview {open}` (`features/overview.js`, the page grid over the stage, key `O`; it also exports `openOv()`, `closeOv(k?)` and `ovTimes`, and keeps its own pdf.js document for thumbnails).
- `registerKey(keys, fn, {help: [label, text], view: 'feed' | null, order, repeat})`. The keys overlay is generated from these help entries. Key auto-repeat is ignored unless `repeat: true`.
- `registerStepper(fn, order)`: `fn(dir, e)` returns true when it handled an Advance (`dir` 1) or Back (`dir` -1) step. `features/back.js` answers Back from its undo stack; otherwise Advance turns the page and then moves to the next item, and Back turns back.
- `registerSection({id, title, order, render(it, i) → Node | null})` adds a side-panel section, rendered as `#sec-<id>`. Built-in orders: why 10, summary 20, outline 30, note 40, related 50, today 60.
- `registerView(name, {label, key, order, roots: () => [elements], show(), hide()})` adds a top-level view. Create its root element inside `#main`. Feed and Wall are views too.
- `registerTextSource(async ({i, it}) → {words, start} | null)` (`text.js`). A word is `{text, page, range?, el?}`.
- `state.stepHook(d)`: a mode that owns the wheel answers a `gesture:step` first (`nav.js` asks it; true = handled). Read-aloud uses it to move the voice a sentence a notch.
- Read-aloud (`features/readaloud.js`) is a mode: while it is on (`html.ra-on`), a capture-phase key handler takes ← → h l Space ↑ ↓ Esc ahead of `chrome.js` and `riffle.js` (not from the library list or the Settings sheet; Esc closes an open sheet first), a click on a word reads from it, a jump (`nav` `page` or `random`) takes the voice along while a turn only holds the follow for 5 s, it never follows from inside a `spread:rendered` handler (that runs within `showFeed()`, before the turn's `nav` event), and the player sits in `#stage` under `#spread` (the pages shrink to make room). It exports `registerEngine({id, label, kind: 'events' | 'audio', sizes, voices(), available(), speak(...)})` for more voices (an `audio` engine returns `{buf | blob | url, wordTimes?}` for a passage), `readAloud` (`start(opt)`, `stop()`, `on`, `playing`), `readAloudPrefs`, `setReadRate` and `setReadVoice('engine:voice')`.

### Units

- **Raster items (scan, pdf):** page `k` is 0-based. `state.start` holds the first page shown.
- **Flow items:** `state.start` holds a *column*. Stable pages (`data-vp` on blocks, about 280 words each) are what summaries cite, the strip shows and `goPage(k)` takes.

### Images and dead links (`features/rescue.js`, `server/rescue.mjs`, `server/routes/14-media.mjs`)

Every image in a flow document loads through `GET /img?u=` (a `flowFilters` hook rewrites `src` and `srcset`; the original stays in `data-orig`). The server fetches it once into the disk cache and checks it: HTTP errors, a web page instead of an image, and placeholders (imgur's removed.png and its region block, found by a canary at startup; Flickr, Photobucket and Tinypic placeholders; 1x1 pixels; identical bytes behind different ids on an image host; images the reader flags) count as broken. A broken image is looked for in the post's own other copies (srcset), mirrors (https, i.imgur.com forms, Wikimedia originals, Substack's proxy) and the Wayback Machine (availability API, then CDX; the raw `id_` snapshot), and served with `X-Stacks-Via`. In the reader an image of unknown fate reserves a small box, an unavailable one becomes a one-line chip (alt text, links to the original and the archive, "fix…" to paste a copy), and a rescued one says where it came from on hover. A scavenger retries what is still broken every few hours (`POST /rescue/run`); with `STACKS_RESCUE_AI=1` it also asks Claude, with web search, for other copies, checks each before use, and spends from the summaries' daily budget. State and a log of rescues: `CACHE/rescue.json`; counts in `/status` (`rescue`).

## Data

- `build-corpus.mjs` writes `corpus.json` from the LessWrong/Alignment Forum APIs, `data/lanes/*.json` (curated lane files) and `seeds.json`.
- `enrich.json` (optional) adds per-item `rel` (0–1 relevance), `hook` (one line) and `best` (0-based best pages).
- The library tree (built at the end of `build-corpus.mjs`; `--tree-only` redoes just this): every item has `path` (folder names under its lane, outermost first) and `ord` (its place in the lane's tree order, depth-first, so it also orders items within a folder). The QURI wikis follow each site's own Starlight sidebar; the other lanes get topic, year or era folders. `laneOrdered` (`corpus.js` `LANE_ORDERED`) names the lanes whose order matters (a wiki page opened from another lane stays in its site). The By topic sort (`state.js` `topicRank`) walks this tree; `features/library.js` draws it in the side panel in exactly that order (a flat list of `state.order` in the other sorts, or when search results or more like this made the order), so j moves the highlight to the next item row.
- Tags (`data/tags.json`, written by a model from the corpus; `STACKS_TAGS` points elsewhere): `{built, source, tags: [{id, label, kind, desc, items: [item ids]}]}`, kind one of topic, method, org, series, benchmark, genre, era, community. `server/routes/46-tags.mjs` serves it cleaned at `GET /tags.json` (404 while absent; re-read when its mtime changes). `features/tags.js` adds derived tags (first author shared by 2+ items, each folder level of `path`, year and last 12 months within the lane, the source when it narrows the lane, the lane in All) and shows the current item's as "Stay in" chips under the side panel's Item | Library tabs, on `item:settled`; a click is `stack.js` `stayIn({kind: 'tag', id: 'tag:<id>' | 'author:…' | 'year:…', …})` (folders: `folderStack`). Exports `chipsFor(i)` and `firstAuthor(a)`; `;` / `:` cycle the chips.

## Profiles (compiled documents)

A profile is an item compiled once and kept on disk: how to show it and what is in it (`docs/profiles/spec.md`, sections 3-7 and 9). Everything that uses one works the same without it.

- `ui/js/profile-core.js` is pure (no DOM, no imports; Node imports it too): `analyzeLum` (ink box, blank page, gutter from a 240-px-wide luminance grid; `render.js`'s `analyze()` calls it), `textLines`/`bodySize`/`headsOf` (headings from pdf.js text by size and weight), `pageRoles` and `rangesOf` (cover, front matter, contents, body, references, appendix, index), `cropGroups` and `cropOf` (one crop box shared by the body pages, recto and verso for scans, a landscape group; pages that would lose ink get their own), `layoutOf`, `spreadStarts`, `snapStart`, `spreadAt` (blank pages ride along, wide pages stand alone, printed facing pages pair), `tocFromHeads`, `hintsOf`, `finalize` (raw analysis to a profile), `validate`, `budgetFor`, `SCHEMA`, `GEN` (bump it when an algorithm changes: stored profiles are then recompiled in idle time) and `HINTS`.
- `ui/js/profile.js` (core): `profileOf(it)` (sync: a profile, `null` or `undefined` when not asked yet), `loadProfile`, `loadProfiles` (one request for the next items), `cropOf`, `pageAspect`, `itemAspect`, `displayFor`, `assetUrl`, `spriteCell` (CSS for a page's cell of the sprite sheet), `preloadSprite`, `cropKey` (part of render keys); `state.useAssets` and `state.useProfiles` switch the stored images, or profiles altogether, off. Emits `profile:updated {id, profile}`.
- Consumers: `render.js` (a blank page is known without drawing it; a display image, decoded and cropped off the main thread with `createImageBitmap` into a `bitmaprenderer` canvas, stands in for a pdf.js render when it is at least 0.9 × `RENDER_H` tall; otherwise pdf.js draws and the profile's crop is used without `getImageData`; panels carry `src: 'asset' | 'pdfjs' | 'scan'`), `feed.js` (exact placeholders and the number of pages that fit before the first paint, spreads from `spreadAt`, the sprite cell as a placeholder, track scrubbing and the page strip from the sprite), `prefetch.js` (`startOf` skips front matter; `planAround` prepares exactly the spreads ahead, loads the next 10 items' profiles in one request, and prepares an unopened PDF's first spread from its images without parsing it).
- `ui/js/features/compile.js` makes them, in idle time: one unit per `requestIdleCallback` with more than 8 ms left, paused by any `nav` (a render under way is cancelled), while the pointer is on the track and for 1.5 s after any key, wheel or click (8 s for the figures pass), until 300 ms after the next `spread:settled`; a unit stuck on the network does not hold up the others after 15 s; PDFs of items ahead only when already on the server's disk. The current item (analysis, text, sprite, figures through figpeek's `regionsOf`), the next 3 (analysis and sprite), the next 4-10 (analysis), the next 11-50 (PDFs already on disk). Its own pdf.js worker (`disableFontFace`). Write-back: pages pdf.js drew for the feed become display images (`toBlob`, WebP 0.8, one per unit) with priority 90 for the opening spread, 70 for best pages and 60 for the rest. Also `window.__stacksCompile(id, {assets, all})` for the batch, `compileTimes`, `compileState()`, and the `profile` track layer (front matter, references, appendix and index as faint bands). Settings in `store`: `compile`, `compileAhead` (10), `writeBack`, `useAssets`.
- Server: `server/profile.mjs` stores them in `CACHE/profiles/<pid>/` (`profile.json`, `text.txt`, `s<j>.webp` sprite sheets, `d<k>.webp` display images, `t<k>.webp` thumbnails) with `index.json`, merges uploads (a `browser` or `playwright` analysis outranks `poppler` at the same `gen`), admits display images by priority within `budgetFor(n)`, marks profiles stale (`gen`, or `src` when the cached source's sha1 changed), maps arXiv LaTeXML sections to pages for the contents, and exports `readProfile(id)` and `profileTextPath(id)`. It registers with `cache.mjs` as a tenant (`registerTenant`, `tenantGrew`), so profiles count toward `STACKS_CACHE_MAX` and leave in LRU order, display images long before the JSON, sprite and text; `STACKS_PROFILE_MAX` (4 GiB) caps the images on their own. Routes in `server/routes/90-profile.mjs`: `GET /profile`, `GET /profiles?ids=` (`&full=1`), `POST /profile`, `POST /profile/text`, `POST|GET /profile/asset`, `POST /profile/forget`, and `profiles` in `/status`.
- `compile.mjs`: the batch (`--engine playwright` runs `__stacksCompile` in headless Chromium; `--engine poppler` uses `pdfinfo`, `pdftoppm` and `pdftotext` for PDFs; neither is required). `ui/js/profile-bench.js`: the benchmark (`?bench=profile` in your own browser).
- Tests: `node --test test/profile-core.test.mjs test/profile-api.test.mjs test/profile-compile.test.mjs`; `node test/profile-bench.mjs --port 4747` runs the benchmark in headless Chromium (Playwright).

## Reading guides (augmentation)

One model call per item writes a reading guide: a skim path of 4-8 stops, skip ranges, a section map with one line each, a glossary, margin notes anchored to verbatim quotes, explanations of the figures a profile found, display hints, a hook and tags (`docs/profiles/spec.md`, section 8).

- `server/augment.mjs` does the work: the text (`textFor()`: the request's text, else the profile's `text.txt`, `pdftotext` on the cached PDF, the scan's OCR, the cached post with tags stripped; capped at `STACKS_AUG_CHARS`, 90,000), the facts the model is told (contents, ranges, figures, the cached summary's gist and key points to complement, the item's entry in `data/highlights.json`), `AUG_PROMPT` and the output schema (`PROMPT` is its version), `checkAugment()` (every quote checked with `findQuote()` from `30-summarize.mjs`; notes whose quote is not found are dropped, other unverified quotes removed; pages clamped, sorted, kept out of the references and skips), `validateAugment()`, `mockAugment()` and Message Batches. Guides live in `CACHE/augment/<sha1(id|model)>.json`, never evicted; batch bookkeeping in `CACHE/augment/batches/`.
- `server/routes/91-augment.mjs`: `GET /augment`, `POST /augment` (NDJSON, as `/summarize`), `GET /augment/stream`, `POST /augment/forget`, `POST /augment/batch`, `GET /augment/batch`, `GET /augment/batches`. It calls the model through `app.ai`, which `30-summarize.mjs` sets (`generate`, `reserve`, `charge`, `costOf`, `spendInfo`, `pickModel`, `MOCK`, `client`), so summaries and guides share one daily budget and one `spend.json`.
- `augment-batch.mjs`: the corpus (or lanes, or ids) as one batch at half price, with an estimate and a question first.
- `ui/js/features/augment.js` (and `ui/features/augment.css`): loads the guide on `item:settled`, makes one after `augDelay` (15 s), panel sections `guide` (25), `sections` (31; hides the built-in outline while it shows) and `glossary` (36), margin notes placed on `spread:settled` from `currentWords()`, a stepper (order 30) that walks the skim path when `store('skim')` is on (key `T`), and a track layer. Exports `augOf(it)`, `skimStops(it)`, `makeAug(it)`; emits `augment:updated {id, aug}` and `nav {type: 'tour', i, it, k}`.
- `feed.js` `registerTrackLayer(name, fn)` and `repaintTrack()`: `fn({i, it, n, s, c, el})` paints in `el`, a `div.tr-layer[data-layer=name]` in the track's bar, emptied when the item changes. It runs on every `paintTrack`, so a layer returns at once when nothing changed.
- Tests: `node --test test/*.test.mjs` (`test/augment-core`, `-api` against a mock-mode server, `-batch` with a stand-in SDK client).

## Finding new material: agent jobs, not an in-app crawler

The app does not search the web for new material itself. It learns from your reading (the learned profile reweights the "For you" ranking) and turns that, plus the library's own gaps (items that fail to open, blocked images, untagged items, problems you flag), into **open jobs**: one Markdown file per job in `jobs/open/`. An outside agent, such as Claude Code pointed at this repository, picks them up by following `jobs/README.md`, edits the data files directly, checks its work with `node jobs.mjs check <id>`, and closes the job (`jobs/done/`). Items an agent adds carry provenance (`added`, `job`, `via`, `why`) and a NEW badge until read. Job files never contain reading history: the repository is public. Design and build notes: `docs/learning/spec.md` (being written; it replaces an earlier plan for in-app discovery).
